# `@bacons/apple-targets` — Current Implementation Spec

Audit date: 2026-07-13. Describes what exists on `auto-tracker-rules` as of this
commit — no implementation code was changed to produce this document.

## 1. Wiring

- **`package.json:16`**: `"@bacons/apple-targets": "^4.0.6"` (direct dependency).
- **`app.json`**: config plugin registered at the end of the `plugins` array
  (`app.json:69`, alongside `expo-router`, `expo-splash-screen`, `expo-font`,
  `expo-image`, `expo-web-browser`, `expo-calendar`).
- No direct reference to `@bacons/xcode` anywhere in the repo (`package.json`,
  app config, or source) — it's only a transitive dependency of
  `@bacons/apple-targets` (used internally to inject targets into the
  generated Xcode project during prebuild).
- **App Group**: `group.com.aexomir.Chrona`, declared in three places that
  must stay in sync:
  - `app.json` → `expo.ios.infoPlist.AppGroupIdentifier` and
    `expo.ios.entitlements["com.apple.security.application-groups"]`
  - `targets/widget/expo-target.config.js` → entitlements, computed as
    `` `group.${config.ios.bundleIdentifier}` ``
  - `targets/watch/expo-target.config.js` → same computed entitlement
  - `storage/widget-storage.ts:5` hardcodes the literal string
    `"group.com.aexomir.Chrona"` rather than deriving it from config.
- `app.json` also sets `expo.ios.infoPlist.NSSupportsLiveActivities: true` at
  the main-app level (required for `ActivityKit.Activity.request` to work).
- **`ios/`** is gitignored (`.gitignore: /ios`) — it's fully regenerated by
  `expo prebuild`, which is where `@bacons/apple-targets` reads
  `targets/*/expo-target.config.js` and materializes native Xcode targets
  (widget extension target, watch app target) with their own Info.plist,
  entitlements, and asset catalogs, wired into the main app target's
  embedded-extension build phase.

## 3. Widget extension — kinds and supported families

Both widgets and the Live Activity live in the same WidgetKit extension
target (`targets/widget/`), bundled by a single `WidgetBundle`.

**Note:** the `@main` attribute is declared **twice** — once in
`targets/widget/widgets.swift` (`struct exportWidgets: WidgetBundle`) and once
in `targets/widget/index.swift` (identical `struct exportWidgets: WidgetBundle`,
byte-for-byte the same body). Only one `@main` can exist in a target; whichever
file the build picks up first "wins" and the other is effectively dead code
sitting in the target. This is a duplication worth resolving, not a feature.

### 3.1 `ChronaTimeWidget` (kind: `com.aexomir.ChronaTimeWidget`)

- **Families**: `.systemSmall`, `.systemMedium` (`.supportedFamilies([.systemSmall, .systemMedium])`)
- **Data source**: `focus_data` key in the App Group `UserDefaults` suite,
  loaded via `ChronaWidgetData.load()`
- **Refresh policy**: `TimelineProvider` requests a reload `1` minute out
  while `isTracking == true`, else `5` minutes out
- **Displays**:
  - Small: "CHRONA" header, live badge when tracking, total focus time today
    (`focusMinutesToday`), and either a running `Text(startDate, style: .timer)`
    (live-updating system timer text) + project name/icon when tracking with a
    project, or a rotating idle suggestion string cycled every minute from a
    fixed 6-item list (`suggestionTexts`)
  - Medium: same left column, plus a right column — `TrackingRightView`
    (project icon/name/title + live timer) when tracking with a project, or
    `IdleRightView` ("START" / play icon / suggestion / "Tap to begin") when
    idle
- **Deep link**: none set on this widget (no `.widgetURL`)

### 3.2 `TimelineWidget` (kind: `com.aexomir.TimelineWidget`)

- **Families**: `.systemMedium`, `.systemLarge`
- **Data source**: `timeline_data` key in the same App Group `UserDefaults`
  suite, loaded via `TimelineWidgetData.load()`
- **Refresh policy**: `1` minute out while `isTracking`, else `15` minutes
- **Displays**: a vertical list of today's sessions (dot + connector timeline
  style), each row showing title, project icon/name, and either a live
  `.timer`-style running duration (if `isActive`) or a static formatted
  duration, plus start time. Medium shows up to 3 rows + "+N more"; Large
  shows up to 6 rows + "+N more". Header shows a "LIVE" badge (colored by the
  first/active session's project color) when tracking, else a static "TODAY"
  label.
- **Deep link**: `.widgetURL(URL(string: "chrona://(tabs)/timeline"))` on both
  Medium and Large layouts — tapping the widget opens the Timeline tab

## 4. Live Activity — `WidgetLiveActivity`

- **Attributes type**: `ChronaActivityAttributes` (defined identically in two
  places — see §6 known-duplication note)
- **`ContentState`** (the only mutable fields once an activity is running):
  `startDate: Date`, `title: String`, `projectName: String`,
  `projectIcon: String`, `projectColor: String`
- There is **no static/fixed data** on `ChronaActivityAttributes` itself
  (empty attributes struct) — everything the UI needs is passed through
  `ContentState` at start and on each update.

### Layout states

| State | View | Content |
|---|---|---|
| Lock Screen / Notification Center banner | `ChronaLockScreenView` | Icon in tinted circle, session title, project name (color-tinted), live `.timer` text (22pt monospaced), and a "Stop" link button (`chrona://stop`) |
| Dynamic Island — Expanded, leading | `ChronaDILeading` | Icon circle, title, project name |
| Dynamic Island — Expanded, trailing | `ChronaDITrailing` | Live `.timer` text |
| Dynamic Island — Expanded, bottom | inline in `WidgetLiveActivity.body` | "Stop" button (`chrona://stop`) |
| Dynamic Island — Compact, leading | `ChronaDICompactLeading` | Small project-colored SF Symbol only |
| Dynamic Island — Compact, trailing | `ChronaDICompactTrailing` | Live `.timer` text, 12pt |
| Dynamic Island — Minimal | `ChronaDIMinimal` | Project-colored SF Symbol only, 14×14 |

- `keylineTint` on the Dynamic Island is set to the project color.
- The Dynamic Island's overall `.widgetURL` is `focus://timer` — **note this
  uses a different URL scheme (`focus://`) than the rest of the app
  (`chrona://`)**, which uses `chrona://` everywhere else (Timeline widget
  deep link, Lock Screen/DI Stop buttons both use `chrona://stop`). This is
  either an inconsistency or the `focus://` scheme is simply unhandled by the
  app's router.
- Colors are resolved from a hex string (`projectColor`) via a `Color(hex:)`
  initializer; falls back to `.green` (Live Activity) or `.blue` (widgets) if
  parsing fails or the string is empty.

## 5. Data flow: RN → native

### 5.1 Widget data (via `ExtensionStorage`)

```
storage/widget-storage.ts
  └─ new ExtensionStorage("group.com.aexomir.Chrona")
       .set("focus_data", {...})      // ChronaTimeWidget
       .set("timeline_data", {...})   // TimelineWidget
  └─ ExtensionStorage.reloadWidget()  // called only after focus_data write
```

- `ExtensionStorage` (from `@bacons/apple-targets`) writes JSON-serializable
  values into the shared App Group `UserDefaults` suite under the given key —
  this is the same storage the widget's Swift `UserDefaults(suiteName:)` /
  `defaults?.data(forKey:)` reads back in `ChronaWidgetData.load()` /
  `TimelineWidgetData.load()`.
- **`syncWidgetData()`** (`storage/widget-storage.ts:18`) computes
  `focusMinutesToday` (sum of today's session durations, floored to minutes),
  tracking state, current session elapsed minutes, start timestamp, title,
  and project fields, writes them to `focus_data`, then calls
  `ExtensionStorage.reloadWidget()` to force WidgetKit to re-render
  immediately (bypassing the timeline's natural refresh cadence).
- **`syncTimelineData()`** (`storage/widget-storage.ts:59`) builds the
  `timeline_data` sessions array (in-progress session first if tracking, then
  today's completed sessions newest-first) and writes it to `timeline_data`.
  **It does not call `reloadWidget()`** — the Timeline widget only picks up
  new data on its own `TimelineProvider` refresh cadence (1 or 15 minutes
  out) or whenever the OS happens to reload it for another reason (e.g. the
  Chrona-widget reload also triggers a WidgetKit family-wide relayout in
  practice, but there's no explicit call forcing `TimelineWidget` specifically).
- Both functions are guarded by `if (process.env.EXPO_OS !== "ios") return;`
  — no-ops on Android/web.
- **Call site**: `features/watch/use-widget-sync.ts`'s `useWidgetSync()` hook,
  invoked once in `app/_layout.tsx:30`. It runs `sync()` immediately on mount,
  then on every change to `useSessionsStore`, `useTimerStore`, or
  `useProjects`, debounced 300ms.

### 5.2 Live Activity (via the `ActivityController` native module)

```
features/watch/use-widget-sync.ts (same hook as above, same sync())
  └─ ActivityController.startActivity({...})   // isTracking flips false→true
  └─ ActivityController.updateActivity({...})  // isTracking stays true
  └─ ActivityController.endActivity()          // isTracking flips true→false
```

- `ActivityController` is a **separate custom Expo native module**
  (`modules/activity-controller/`), not part of `@bacons/apple-targets` — it's
  the RN↔ActivityKit bridge that starts/updates/ends the Live Activity from
  the main app process. It duplicates the `ChronaActivityAttributes` /
  `ContentState` struct definition from the widget extension
  (`modules/activity-controller/ios/ActivityControllerModule.swift:4-12` vs.
  `targets/widget/WidgetLiveActivity.swift:5-13`) — the two must be kept in
  sync by hand since they're compiled into different targets and Swift has no
  shared-header mechanism across an app target and an extension target here.
- `startActivity`: first ends **all** existing `ChronaActivityAttributes`
  activities (`Activity<ChronaActivityAttributes>.activities`), explicitly to
  clean up orphaned activities from a prior crash/kill, then requests a new
  one with `pushType: nil` (local-only, no remote push updates).
- `updateActivity`: updates `Activity<ChronaActivityAttributes>.activities.first`
  — i.e. it always operates on whatever the **first** activity in the array
  is, not a specific tracked activity ID. `startActivity`'s result includes
  an `activityId`, but nothing on the JS side (`use-widget-sync.ts`) stores or
  passes it back into `updateActivity`/`endActivity` — those calls don't
  reference an ID at all, they act on `Activity<ChronaActivityAttributes>.activities`
  broadly. In the normal single-activity case this is harmless, but see §6.
- `endActivity`: ends **all** activities of this type, again not scoped to a
  specific ID.
- `isLiveActivityRunning()`: sync function, unused by any current call site
  found in the repo (`ActivityController.isLiveActivityRunning` has no
  callers outside `modules/activity-controller/`).
- Gated behind `#available(iOS 16.2, *)` in all four functions — no-ops
  (resolve empty/void, don't throw) on older iOS.
- **Call site**: same `useWidgetSync()` hook, same debounced `sync()`, driven
  off a `wasTrackingRef` ref that tracks the previous `isTracking` value to
  decide start vs. update vs. end. All three calls are fire-and-forget
  (`.catch(() => {})`), so failures are silently swallowed — no user-visible
  error surfaces if e.g. `Activity.request` throws (activity limit reached,
  Live Activities disabled in Settings, etc.).

### 5.3 Watch target data flow (adjacent, not part of widget/Live Activity)

The watch app itself is created by `@bacons/apple-targets` (`type: "watch"`),
but its runtime data channel is a **third, separate custom native module**,
`modules/watch-connectivity/`, using `WCSession` (not the App Group / not
`ExtensionStorage`):

```
features/watch/use-watch-integration.ts (useWatchIntegration, called in app/_layout.tsx:31)
  └─ sendToWatch({ isTracking, title, projectName, projectColor,
                   startTimestamp, todayMinutes, todaySessions,
                   recentProjects: JSON string, recentSessions: JSON string })
       └─ modules/watch-connectivity native module
            └─ WCSession.default.sendMessage(...)              if reachable
            └─ WCSession.default.updateApplicationContext(...)  fallback otherwise
                 └─ targets/watch/ContentView.swift's WatchSession.applyMessage(_:)
                      decodes and republishes as @Published fields
```

- Reverse direction: watch button presses (`start`/`stop`/`startWithProject`/
  `updateTitle`) call `WatchSession.sendAction(_:)` →
  `WCSession.default.sendMessage` → received by
  `modules/watch-connectivity`'s `WCDelegate` → emitted as JS event
  `onWatchMessage` → `useWatchMessages` in `use-watch-integration.ts` drives
  `useTimerStore`/`useSessionsStore` actions.
- `recentProjects` / `recentSessions` are JSON-stringified before sending
  because, per the code comment, "WC dict doesn't support nested arrays" —
  they're decoded again on the watch side with `JSONDecoder`.
- This whole path is included here because it shares the `targets/watch/`
  directory and the App Group entitlement with the widget, but the entitlement
  is not actually used for data transfer on the watch path — `WCSession` is
  the transport, not `UserDefaults(suiteName:)`.

## 6. Known duplication / consistency risks (structural, from reading the code)

These are **not confirmed bugs** — they're places where the code's own
structure creates a way for two copies of something to drift out of sync,
flagged so they can be checked against the "bad UI adjustments" and
"sometimes Live Activity issues" the user has observed but hasn't pinned down
yet:

1. **Two `@main` `WidgetBundle` declarations** in the same target
   (`targets/widget/widgets.swift` and `targets/widget/index.swift`, identical
   bodies). Whichever the build system picks up is the one that actually
   ships; the other is inert but still compiled. If they ever diverge (e.g.
   someone edits one and not the other, which — given they're currently
   byte-identical — looks exactly like a copy that was never cleaned up),
   whichever one "wins" silently determines behavior.
2. **`ChronaActivityAttributes` defined twice**, once in the widget extension
   (`targets/widget/WidgetLiveActivity.swift`) and once in the main app's
   native module (`modules/activity-controller/ios/ActivityControllerModule.swift`).
   Both currently match field-for-field, but nothing enforces that — a change
   to one without the other would fail to compile only if the mismatch
   affects `Codable`/`Hashable` conformance in an incompatible way, and could
   otherwise silently produce activities the widget extension can't decode
   correctly.
3. **`updateActivity`/`endActivity` act on `Activity<ChronaActivityAttributes>.activities`
   broadly** (first / all) rather than a specific ID returned from
   `startActivity`. Correct today because the app only ever intends one
   Chrona activity to exist, but there's no code-level guarantee against a
   race (e.g. two `startActivity` calls firing close together before the
   first `.request()` resolves) creating more than one, after which
   `updateActivity` would only ever touch `.first` — a plausible source of
   "Live Activity shows stale/wrong data sometimes."
4. **`focus://timer` vs. `chrona://` scheme mismatch** on the Dynamic Island's
   `.widgetURL` (§4) — worth checking whether tapping the compact/minimal
   Dynamic Island actually opens the app, since `focus://` doesn't appear to
   be a scheme this app registers anywhere else.
5. **`syncTimelineData()` never calls `ExtensionStorage.reloadWidget()`**
   (§5.1) — the Timeline widget's data can go stale between its own 1/15-minute
   provider refreshes even when `syncWidgetData()` (which does reload) fires
   moments earlier with fresh session data, since a per-kind targeted reload
   API isn't used (`reloadWidget()` reloads the whole family, but only one of
   the two sync functions ever calls it).
6. **All three `ActivityController` calls in `use-widget-sync.ts` are
   fire-and-forget** (`.catch(() => {})`) — if `Activity.request` throws
   (activity budget exceeded, Live Activities toggled off in system settings,
   etc.), there's no retry, no user-facing message, and no state reconciliation
   — the app's `isTracking` state and the actual Live Activity state can
   silently diverge.
7. **Idle-state widget copy is client-computed pseudo-randomness**: both
   `ChronaTimeWidget`'s idle state and `IdleRightView` pick from a fixed
   6-string list (`suggestionTexts`) indexed by
   `Int(Date().timeIntervalSince1970 / 60) % 6` — i.e. it changes every
   minute in wall-clock time regardless of widget refresh cadence, so the
   *displayed* string can be stale relative to what the formula would
   currently produce whenever the widget hasn't been reloaded recently. Not a
   crash, but a plausible source of "the suggestion text looks wrong/stuck."

## 7. Reported-but-unconfirmed issues (per user, 2026-07-13)

The user indicated there are "bad UI adjustments" and "sometimes Live
Activity issues" but didn't have specifics on hand. §6 above lists the
structural candidates most likely to produce exactly those symptoms
(items 3, 4, 6, 7 for Live Activity; layout/format code in §3–4 generally for
UI). Recommend reproducing with the Live Activity visible (Lock Screen +
Dynamic Island, both compact and expanded) while toggling tracking on/off
and switching projects mid-session, to narrow down which of the above is the
actual cause before changing code.
